# Gow/theFlow Chat

A small browser-based messaging starter intended for GitHub Pages + Supabase. It includes email/password auth, public user discovery, one-to-one text chat, image/video uploads, 12-hour expiry, and experimental one-to-one WebRTC calls.

**This project is a starter, not a production-audited Messenger replacement.** The code has been generated but not connected to or tested against your Supabase project. Calls can fail on some networks without a TURN relay. The cleanup function must be deployed and scheduled before the app can promise backend deletion.

## Included

- `index.html`, `styles.css`, `app.js`: browser app.
- `config.js`: paste your Supabase project URL and anon/publishable key here.
- `supabase/schema.sql`: tables, trigger, RLS policies, private media bucket.
- `supabase/functions/cleanup-expired/index.ts`: server-side removal of expired messages and uploaded media.

## 1. Create a Supabase project

1. Open https://supabase.com/ and create a project on the free tier.
2. In Project Settings → API, copy the **Project URL** and **anon/publishable key**.
3. Edit `config.js` and replace the two placeholder strings.
4. Never paste a `service_role` / secret key into `config.js`, HTML, or any file committed to GitHub.

## 2. Set up the database

1. In Supabase, open SQL Editor → New query.
2. Paste all of `supabase/schema.sql` and run it.
3. In Authentication → URL Configuration, add your eventual GitHub Pages URL to **Site URL** and **Redirect URLs**. For a project named `gow-theflow-chat` under username `YOUR_USERNAME`, the URL is usually `https://YOUR_USERNAME.github.io/gow-theflow-chat/`.
4. In Authentication → Providers, ensure Email is enabled. For a quick private test you can disable email confirmations, but for a public app keep confirmation enabled and configure email delivery.
5. In Database → Replication (or the Realtime settings for your Supabase UI), enable Postgres Changes for `public.messages`. The UI and menu names may vary.

The SQL makes profiles discoverable to authenticated users, but only the sender and recipient can read a message row. This is a public-registration app: anyone can create an account and discover registered users. Add rate limits, moderation, blocking/reporting, and abuse prevention before sharing widely.

## 3. Enable genuine 12-hour cleanup

The `expires_at` field is generated by PostgreSQL from `created_at + 12 hours`; the browser cannot set it. The app stops displaying messages as soon as their expiry time passes, but **actual row and media deletion requires the scheduled Edge Function below**.

Install the Supabase CLI (https://supabase.com/docs/guides/cli) and log in, then from this project directory run:

```sh
supabase login
supabase link --project-ref YOUR_PROJECT_REF
supabase secrets set SUPABASE_URL=https://YOUR_PROJECT_ID.supabase.co
supabase secrets set SUPABASE_SERVICE_ROLE_KEY=YOUR_SERVICE_ROLE_KEY
supabase functions deploy cleanup-expired
```

`YOUR_SERVICE_ROLE_KEY` is a server secret. Never commit it. The Supabase CLI reads the secret from your terminal; do not paste it into source code.

### Schedule cleanup

Use Supabase Cron / Scheduled Edge Functions in your project dashboard to invoke `cleanup-expired` every 5 minutes. Configure the invocation with the function's normal authorization mechanism as required by your Supabase project. For a simple setup, set a secret:

```sh
supabase secrets set CLEANUP_SECRET=MAKE_A_LONG_RANDOM_SECRET
```

Then configure the scheduled request to send header `x-cleanup-secret: MAKE_A_LONG_RANDOM_SECRET`. Keep that secret only in the scheduler, not in this repository. Depending on the Supabase dashboard version, scheduling may be under Edge Functions → Schedules or Integrations/Cron. Follow the current Supabase docs: https://supabase.com/docs/guides/functions/schedule-functions.

The function deletes up to 500 expired message rows per run and deletes associated files first. If there is a deletion error, it returns an error and retains the affected message rows for retry. Increase batch size or run more frequently if your app grows.

**Important:** do not promise exact-to-the-second physical deletion. Messages become expired at 12 hours and are hidden immediately by the client/query; the scheduled backend removes stored rows and media on the next successful run, normally within about five minutes of expiry.

## 4. Publish on GitHub Pages

1. Create a new GitHub repository, e.g. `gow-theflow-chat`.
2. Upload the contents of this folder to the repository root. `index.html` should be at the root, not inside another nested folder.
3. On GitHub, open Settings → Pages.
4. Under Build and deployment, choose **Deploy from a branch**, branch `main`, folder `/ (root)`, then Save.
5. Wait for the Pages deployment to finish. Open the Pages URL and test on HTTPS.
6. Add that exact URL to Supabase Authentication → URL Configuration / Redirect URLs.

No build step is needed. GitHub Pages hosts static files only; Supabase provides authentication, database, storage, and realtime services.

## 5. Test two accounts

1. Open the Pages URL in one browser, create account A.
2. Open a second browser/profile or device, create account B.
3. Search for the other profile and start a chat.
4. Send text and a small image/video.
5. Confirm that only the two chat participants can see the messages.
6. To test expiry without waiting 12 hours, use a separate development-only SQL query to inspect `created_at` and `expires_at`. Do not modify production data to simulate expiry.

## Voice and video calls

The starter uses browser WebRTC for media and Supabase Realtime Broadcast for signaling. It requests camera/microphone access only when a call starts. Use HTTPS and allow browser permissions.

The included ICE config uses a public STUN server only. STUN is not enough for every carrier, firewall, or NAT type. For reliable calls, configure a TURN relay (for example, a suitable managed TURN provider) and add its credentials to the `ICE` `iceServers` list in `app.js`. Do not commit long-lived TURN credentials to a public repository; use short-lived credentials from a server/Edge Function for production.

The signaling channel in this starter is a simple prototype using a stable per-conversation broadcast channel. Before public use, add authenticated/private-channel authorization and robust call invitation/ringing state. Do not use it for sensitive calls until reviewed and tested on multiple networks.

## Security and limitations

- **Public signup means strangers can register.** User discovery is open to signed-in users.
- RLS limits message rows to sender and recipient. Test the policies using two accounts before launch.
- Supabase anon/publishable keys are intended for browser use only when RLS is configured correctly.
- This app does not provide end-to-end encryption. Supabase and the service operator can access stored message content.
- Photos/videos use a private bucket. The app requests short-lived (5-minute) signed URLs for authorized chat participants. The Storage read policy checks that the object is attached to a message in which the current user is sender or recipient and that the message has not expired. Do not make the bucket public.
- Browsers cannot prevent screenshots, screen recordings, or recipients copying message contents.
- No push notifications, group chat, message edits/deletes, blocking/reporting, spam controls, or moderation dashboard yet.
- GitHub Pages has no backend runtime or scheduled jobs; Supabase is required for dynamic features.
- Free tiers have quotas and policies that can change. Review Supabase pricing and limits before launching publicly.
- The generated source has not been connected to your Supabase project or tested in your environment.

## Troubleshooting

- **Config needed:** check `config.js` values and reload.
- **Profile not created:** check SQL ran successfully and inspect Supabase logs / Auth user creation.
- **No realtime updates:** enable `public.messages` in Realtime/Postgres Changes.
- **RLS error:** rerun schema and verify policies are present.
- **Media fails:** implement signed URLs as described above before use with the private bucket.
- **Calls do not connect:** confirm both users are in the same conversation, permissions are allowed, and configure TURN.
- **Email confirmation links go to the wrong place:** update Supabase Site URL and Redirect URLs.
